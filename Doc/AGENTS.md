# 프로젝트 작업 규칙

- 이야기와 포획의 최신 기준 문서는 `1장 진행내용.txt`다. 일일 1회 포획 제한 대신 약화된 주령에게 봉인권을 소비하는 흐름을 따른다. 실제 구현 범위와 변경 이력은 `패치노트.md` 한 문서에 기록한다.
- 기능 추가·개선·버그 수정·에셋 또는 문서 변경을 완료할 때 `패치노트.md`에 날짜, 변경 내용, 사용법, 남은 사항, 확인 상태를 기록한다. 현재 누적 기준은 1.0.0v이며 이후 완료한 작업 단위마다 1.0.1v, 1.0.2v처럼 마지막 숫자를 1씩 올린다. 같은 요청의 변경은 하나의 버전으로 묶고 최신 버전을 위에 추가하며 상단 현재 버전도 갱신한다.
- 구현 현황이나 작업 안내 문서를 새로 분산 작성하지 않는다. 상세 안내도 패치노트에 통합한다. 기획 원문은 별도로 유지하며, 과거 기록은 보존하고 미구현·실행 미확인 사항을 완료로 표현하지 않는다.
- 기본 HUD는 최소화한다. 상세 정보는 Tab 통합 기록창에 모으고, 중요한 대화·포획·사망 안내만 상황에 따라 표시한다.
- UI는 정보 종류별 독립 영역과 여백을 확보하고, 표시와 클릭에 같은 UIRect 배치를 사용한다. 작은 창의 긴 목록은 페이지로 나누어 내용을 누락시키지 않는다.
- 화면에 배치하는 새 오브젝트는 Actor 인터페이스를 사용하고 SceneGraph에서 부모·수명·그리기 순서를 관리한다. PrototypeScene.cpp의 연결 계층을 확장하며 별도의 숫자 인덱스 렌더 분기나 독립 소유 목록을 다시 추가하지 않는다. 기존 전투·저장 데이터와 장면 표현의 연결을 유지한다.

- 코드 포맷은 저장소 루트의 `.clang-format`을 따른다. 중괄호는 새 줄에 두는 Allman 스타일, 공백 4칸 들여쓰기, 한 줄 한 문장을 사용한다. 짧은 함수와 조건문도 여러 줄로 작성한다.
- 게임은 지역을 탐색해 적을 찾아 사냥하는 RPG로 구현한다. 플레이어 주변 시간제 웨이브 생성은 기본 전투로 사용하지 않는다.
- GLSL은 `SimpleGame/Shaders`의 `.vs`·`.fs` 파일로 관리하고 `ShaderFiles`로 로드한다. 정적 지형·오브젝트 메시는 Renderer 캐시를 재사용한다.
- 함수 및 논리적 처리 단계 사이에는 빈 줄을 한 줄 둔다. 긴 인자 목록은 여러 줄로 나누며 한 줄은 100자를 기준으로 한다.
- 포맷 적용 대상은 프로젝트에서 작성한 C++ 및 독립 셰이더 파일이다. `Dependencies`의 외부 라이브러리와 생성 파일은 수정하지 않는다. C++ 문자열에 포함된 셰이더는 별도의 GLSL 코드로 취급한다.

- 커밋 메시지는 한글로 작성하고 중요한 변경 사항을 제목과 본문에 요약한다.

- 게임 내부 대사, 퀘스트 이름과 설명, 아이템·주령 이름, 도감, 메뉴, 상태 메시지 및 조작 안내는 한글로 작성한다. 키 이름(WASD, E, Q 등)과 기술 식별자는 유지할 수 있다.
- 문자열은 UTF-8로 관리하고 한글을 지원하는 렌더링 경로를 사용한다.
- 사용자가 특별히 요청하지 않는 한 빌드, 실행, 테스트 및 렌더링 결과 확인은 사용자가 담당한다. 에이전트는 코드와 문서를 수정하고 수행하지 않은 검증을 명시한다.
- 이후 NPC는 투명 PNG 스프라이트 시트 기반으로 구성하고 SpriteSheet/SpriteAnimation을 재사용한다. 전용 이미지가 없는 경우 임시 외형임을 명시한다. 8방향 이동과 원화의 실제 방향 수를 구분한다.

## 최초 설계 시 성능 고려사항

- 새 기능·맵·캐릭터·이펙트를 설계할 때 성능 비용도 함께 정한다. 대표 장면에서 50FPS(프레임 간격 약 20ms)를 목표로 하고, 최소 40FPS(약 25ms) 수준을 확인 기준으로 삼는다. 평균 FPS와 함께 P95·P99 프레임 간격 및 긴 멈춤을 기록하며, 실제 사용자 PC에서 측정하기 전에는 목표 달성을 주장하지 않는다.
- 설계 전에 최대 동시 표시 개체 수, 활성 AI 수, 메시·재질·뼈대·파티클 수, 텍스처 크기, 캐시·대기열 메모리 한도와 로딩 시점을 적는다. 구체적인 수치는 현재 장면의 측정값과 남은 프레임 예산을 근거로 정하며 임의의 개체 수 제한으로 퀘스트나 NPC 생활을 삭제하지 않는다.
- 렌더 콜백에서는 파일 쓰기·폴더 전체 검색·전체 데이터 직렬화·대량 임시 할당을 피한다. 필수 초기 로딩과 디스크 읽기는 발생 시점을 명시하고 미리 읽기·프레임 분산을 검토한다. 작업자를 사용할 때는 변경 가능한 월드나 OpenGL 상태를 직접 공유하지 않고 복사한 데이터, 큐 한도, 포화·실패·종료 처리를 설계한다. 게임 저장의 보장과 버려도 되는 파생 캐시를 구분한다.
- 정적 지형·구조물·문자·재질 분류·애니메이션 메타데이터는 재사용한다. 개별 추가나 변경 때문에 전체 GPU 메시 풀을 다시 올리거나 캐시 전체를 지우는 구조를 피하고, 부분 갱신과 최근 사용 항목 보존을 우선한다. 배칭·인스턴싱은 투명도와 기존 Z-order를 보존하면서 실제 드로우 호출·정점 낭비·상태 변경을 측정한다.
- 화면 밖 렌더링을 걸러내고, NPC·적의 거리와 활동에 따라 AI·경로 탐색·표현 갱신 주기를 나눈다. 가까운 전투·중요 NPC의 반응과 애니메이션의 부드러움을 유지하고, 먼 NPC의 생활·이사·편지·뉴스 등 월드 상태도 유지한다. 갱신 생략 대신 경과 시간 누적이나 제한된 주기 처리를 설계한다.
- 매 프레임 전체 주민·집·적을 중첩 검색하지 않도록 조회 표·공간 인덱스를 재사용하고, 소유자·예약·이사 상태가 바뀔 때의 무효화 기준을 정한다. 모니터링은 읽기 전용 스냅샷과 제한된 전송 주기를 사용하며 JSON 생성과 파일 기록도 성능 예산에 포함한다.
- 반복 진단 이벤트는 집계하고 장면·지역·포커스·해상도·빌드 구성과 CPU/GPU 측정 범위를 남긴다. CPU 렌더 제출·GPU 실행·프레임 간격·타이머 지연을 구분하고 중첩 측정 시간을 더해 원인을 단정하지 않는다. 수집 기능 자체의 비용과 보관량도 고려한다.
- 기능 추가 전후 같은 PC·빌드 구성·해상도·위치·개체 수·캐시 상태로 비교한다. 마을 대기, 이동과 첫 지형 방문, 전투와 Q/R, NPC 밀집, 모니터링 주기, 저장과 장시간 플레이를 확인 대상으로 둔다. 빌드·게임 실행·테스트는 기존 사용자 담당 규칙을 따르며, 실행 자료가 없으면 정적 검토 완료와 성능 검증 대기를 구분한다. 상세 비교 절차는 `패치노트.md`의 1.0.106v에 둔다.
