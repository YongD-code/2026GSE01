# 성능 저하 원인 분석

분석일: 2026-10-28  
대상: 마지막으로 저장된 2026-10-27 16:54~16:56 실행 기록, 기록 버전 1.0.101v  
측정 환경: 기록된 OpenGL 렌더러 AMD Radeon(TM) Graphics, 배칭·디스크 캐시 활성화

## 확인된 현상

사용자는 R을 쓰지 않고 마을에 서 있을 때도 약 15 FPS가 나온다고 보고했다. 현재 확인 가능한 가장 최근 기록은 전날의 약 146초 분량이다. 기록에 각 프레임의 장면과 조작 상태가 없어, 아래 숫자가 그 마을 상황과 정확히 같은 순간이라고 단정할 수 없다. 이번 분석은 기존 기록과 코드 확인이며 게임을 새로 빌드하거나 실행하지 않았다.

| 측정값 | 전체 기록 | 가장 느린 10초 구간 |
| --- | ---: | ---: |
| 프레임 수 | 5,339 | 200 |
| 평균 FPS | 약 36.6 | 약 19.9 |
| 평균 프레임 간격 | 27.30ms | 50.26ms |
| 프레임 간격 95백분위 | 39.28ms | 184.48ms |
| CPU 렌더 제출 시간 평균 | 7.77ms | 27.38ms |
| CPU 갱신 시간 평균 | 2.80ms | 13.81ms |
| GPU 측정 시간 평균 | 3.38ms | 8.25ms |

FPS는 프레임 간격의 평균으로 계산했다. 50 FPS에는 평균 20ms, 40 FPS에는 평균 25ms 정도의 프레임 간격이 필요하다. 기록에서 느린 구간은 이 기준을 크게 넘는다. CPU와 GPU 작업은 겹쳐 실행될 수 있고 측정 범위도 다르므로 각 시간을 단순히 더하거나 빼서 원인을 확정할 수는 없다. GPU 수치는 기록된 OpenGL 쿼리 범위에 한정되며 화면 표시와 드라이버의 모든 지연을 포함하지 않는다.

## 원인별 근거

### 1. 월드 렌더링과 게임 갱신의 CPU 부담

가장 느린 10초 동안 CPU 렌더 제출은 평균 27.38ms, 게임 갱신은 평균 13.81ms로 기록됐다. GPU 쿼리 평균 8.25ms보다 CPU 측정 구간이 길어, 이 구간에서는 CPU 쪽 작업과 지연을 먼저 조사할 근거가 있다. 다만 CPU 수치에는 운영체제의 스케줄링 대기도 포함될 수 있다.

같은 구간의 한 통계 창에서 월드 그리기는 평균 23.73ms, 씬 동기화는 평균 7.61ms였다. `character_3d`는 개체당 평균 0.12ms, 375회 표본으로 기록됐다. 캐릭터 시간은 월드 그리기에 포함되는 중첩 측정이므로 별도로 더하면 안 된다. 현재 3D 캐릭터는 개체별로 별도 렌더 대상과 깊이 버퍼를 사용하고 결과를 합성하므로, 화면에 보이는 인물이 많아질수록 비용이 늘 가능성이 있다. 월드 객체 정렬·가림 처리 비용도 함께 조사할 필요가 있다.

배칭은 이미 활성화돼 있었다. 느린 10초에는 프레임당 평균 약 108회 드로우 호출과, 정점 비율·용량 또는 텍스처 제한으로 기록된 배치 종료 이벤트가 총 5,838회 발생했다. 이벤트는 모든 드로우 호출과 같은 뜻이 아니며 그 자체만으로 병목을 증명하지 않는다. 다만 배칭이 켜져 있어도 상태 변경이나 배치 분할로 호출이 많아질 수 있다는 점을 확인할 대상이다.

### 2. 새 에셋 로딩과 메시 풀 재업로드에 따른 큰 끊김

약 1.23초의 프레임 간격이 나타난 시점 부근에는 묘역 바닥·장식의 캐시 조회, 생성·저장, 메시 풀 업로드 이벤트가 한 프레임에 다수 기록됐다. 해당 시점의 통계 창에는 월드 그리기 최대 1,125.26ms도 남아 있다. 같은 시기의 기록이라 연관 가능성이 높지만, 기록만으로 그 시간 전부가 디스크 때문이라고 확정할 수는 없다.

코드상 새 메시를 설치할 때 `Renderer::UploadPool()`이 기존 메시 풀 전체를 다시 구성해 GPU에 업로드한다. 캐시 저장도 렌더 경로에서 이루어지고 저장 공간 확인을 위해 캐시 파일들을 조회한다. 처음 방문하거나 캐시에 없는 지형을 여러 개 만드는 순간 비용이 겹칠 수 있다. 이것은 지속적인 15 FPS와 구분되는 일시적 멈춤 후보이다. 캐시를 임의로 지우면 첫 로딩 작업이 오히려 늘 수 있다.

### 3. 모니터링과 기타 주기 작업의 지연

느린 구간의 한 통계 창에서 모니터링 처리 시간은 평균 8.86ms, 최대 132.84ms였고 다른 창에서도 최대 122.25ms가 관찰됐다. 게임 스레드에서 상태 수집과 JSON 생성이 수행되며, 네트워크 전송은 별도 작업자가 담당한다. 따라서 이 기록만으로 네트워크 전송이 게임 스레드를 막았다고 볼 수는 없다. 직렬화, 상태 수집, 동기화와 스케줄링 대기 중 무엇이 지연됐는지 추가 측정이 필요하다.

저장 코드에는 동기 파일 쓰기와 `FlushFileBuffers`도 있으므로 주기적인 끊김 후보지만, 해당 작업의 개별 시간 기록이 없어 이번 자료로 영향도를 판단할 수 없다. 성능 기록 자체도 배치 분할 이벤트를 자주 파일에 기록하므로 비용이 일부 있을 수 있으나, 이를 켜고 끈 비교가 없어 크기는 미확인이다.

### 4. 프레임 진행 주기 확인 필요

드로우 호출이 기록되지 않은 프레임들도 중앙값 약 30.51ms 간격으로 나타났다. 코드에는 목표 주기에 맞춰 `glutTimerFunc`를 예약하는 부분이 있다. 하지만 기록에 장면·포커스·타이머의 실제 대기 시간이 없어 이 결과만으로 타이머나 수직 동기화를 원인으로 확정할 수 없다. 화면 상태와 실제 예약·호출 시각을 함께 기록해야 한다.

## 확인 및 개선 순서

1. 사용자가 새 빌드로 같은 해상도와 같은 마을 위치에서 2분 이상 서 있고, 시간과 NPC 수, 포커스 여부, 보이는 FPS를 기록한다. 별도로 이동·전투·사슴 Q 사용 시간도 남겨 각 조건을 구분한다. 기록은 실행 사용자 계정의 `AppData/Local/2026GSE01/Performance`에 생성된다.
2. 같은 위치와 실행 조건에서 모니터링 활성·비활성 기록을 비교한다. 실행 파일이 실제로 읽는 `Data/Monitoring.ini`의 기존 설정을 보존한 뒤 `enabled`를 바꿔 각각 측정하고 원래 값으로 복원한다. 비활성 중에는 모니터링 송신이 중단된다.
3. 메시 풀 업로드, 캐시 읽기·쓰기, 저장, 모니터링 세부 단계와 프레임 타이머의 실제 대기 시간을 나눠 측정한다. 실행 상태와 현재 장면도 기록해야 결과를 마을·전투별로 비교할 수 있다.
4. 측정 결과에 따라 메시 풀의 전체 재업로드를 묶거나 증분 처리하고, 캐시 저장과 목록 조회의 렌더 스레드 비용을 줄인다. 상태 수집과 JSON 생성을 분산하고, 보이는 캐릭터 렌더 및 월드 정렬 비용도 비교해 우선순위를 정한다. 성능 기록의 과도한 이벤트는 집계 방식 또는 선택 가능한 기록 수준을 검토한다.

이번 작업에서는 성능을 개선하는 코드를 변경하지 않았으며, 40~50 FPS 달성을 확인하지 못했다. 사슴 Q의 새로운 이펙트는 이 기록을 만든 실행 이후의 변경이므로 전날 기록에 나타난 저하 원인으로 볼 수 없다.
